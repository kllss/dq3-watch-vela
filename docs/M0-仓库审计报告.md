## 0. 结论摘要

1. **这不是一个游戏骨架，而是一个单页输入探针。** 仓库共 16 个跟踪文件、1 个页面、1 个提交、3 个归档 RPK；没有路由、没有存储、没有测试、没有游戏逻辑。
2. **可以直接复用的"模块"是 0 个。** 可复用的是 4 个工程骨架文件 + 5 段算法/工具函数（排版换算、能力探测、日志、振动、表冠读取），且都需要提取重构后才能进游戏。
3. **可确认的输入只有 4 条：触屏点击、表冠滚动（仅位移）、加速度计（约 11 Hz）、振动两档。** 返回键 3 轮有数据均未触发；陀螺仪/计步/环境光方法不存在；罗盘有回调但不跟手。
4. **v2.0 的自适应排版没有上过机。** 仓库内全部实机读数来自 v1.1–v1.4；v1.4 产物里不含 `432 / W` 与 `layout W=`，v2.0 产物构建时间（23:06）晚于记录的实测时间（22:15）。因此"排版自适应已验证"不成立，只能算"已实现、未实测"。
5. **`lay` 没有在 `private` 中声明。** 模板绑定的是 `_vm_.lay.hudH`。它能显示正确，很可能是因为同一回调里还改了 `status`、随后 `log()` 又改了 `logs`，触发了整页重渲染。这是隐式依赖，不是可靠机制。
6. **`if` 切换视图会销毁 `scroll` 节点，但不会重置 `scrollY` 基线。** 从汇总页返回后，第一次表冠事件可能被算成一次巨大的位移。这个 bug 对探针只是脏数据，对游戏就是"转一格跳十格"。
7. **触摸与表冠存在结构性冲突。** `swipe` 官方明确"滑动方向有滚动条时不触发"；而表冠必须依赖 `scroll` 容器。全屏滚动容器会吃掉滑动手势，二者不能默认共存。
8. **没有 canvas。** 官方组件清单里没有 canvas（`components/basic/canvas.html` 会重定向到概述）；地图只能用 `div`/`text` 拼格子，刷新频率必须按"步进"设计，不能按 60fps 设计。
9. **官方文档明确不建议在手表上使用自定义组件**（"拥有独立的 ViewModel，因此存在一定内存开销"）。所以"拆 `.ux` 组件"不是好方案，正确做法是"单页面 + 纯 JS 模块分层"。
10. **存储与文件在 RW6 上完全未验证。** `@system.storage` 只能存字符串，`@system.file` 有 `readText/writeText/move/readArrayBuffer`，但仓库里没有一行调用，manifest 也没声明这两个 feature。M1 必须把它们当作全新能力来测。

## 3. B. 输入、排版与设备能力的源码分析

### 3.1 入口与生命周期

|---|---|---|
| `onInit` | 145–162 | 生成 40 条测试项；`$canIUse` 探测 sensor/vibrator/event；打印 `DATA_TYPES` |
| `onReady` | 164–215 | `device.getInfo` 取分辨率并算排版；`scrollTo(800)` 预置表冠基线；800 ms 后 `armed=true`；订阅电量事件 |

### 3.2 排版算法（v2.0）

源码位置：`probe/src/pages/Index/index.ux:164-200`。

```js
const W = Number(r.screenWidth) || 432
const H = Number(r.screenHeight) || 514
const k = 432 / W
const dv = (v) => Math.max(1, Math.round(v * k))
const lhDev = Math.max(18, Math.floor(H * 0.66 / 12))
this.lay = {
  hudH: dv(40), title: dv(16), sub: dv(10),
  rowH: dv(38), btnH: dv(36), btn: dv(12), hint: dv(10),
  logbarH: dv(26), miniH: dv(20), mini: dv(9),
  bigH: dv(34), big: dv(13), item: dv(11), log: dv(9),
  sumTitle: dv(17), sumSub: dv(10),
  lineH: dv(lhDev), lineF: dv(Math.round(lhDev * 0.56)),
  det: dv(9), code: dv(8)
}
```

数学上这是对的：

- `designWidth: 432` 表示 1 设计 px = `W/432` 物理 px；
- `dv(v) = v * (432/W)` 设计 px，落到屏幕正好是 `v` 物理 px；
- 因此 `dv()` 的语义是"我要 v 个物理像素"，与设备宽度解耦；
- RW6 `W=432`，所以 `k=1`，`dv(v)=v`。

**但在目标设备上，这套自适应是恒等变换。** 它只能防"分辨率读错/换机型"，不能在 RW6 上把字号"调大"或"调小"。真正的可读性仍取决于 `dv(16)`、`dv(12)` 这些基值选得对不对。

`lhDev` 的口径需要注意：它先按物理像素算出"12 行铺满 66% 屏高"的行高（RW6 上是 28），再 `dv()` 回设计 px。名字叫 `lhDev`，实际是物理 px，容易误读。

#### 排版相关的三个缺陷

1. **`lay` 未声明。** `private`（88–143 行）里没有 `lay`，模板却绑定 `_vm_.lay.hudH`（编译产物可见）。
   - 后果：`this.lay = {...}` 本身不触发响应式更新。
   - 为什么看起来没事：同一回调里先改了 `status`（168 行，已声明），随后 `this.log()` 又改了 `logs`（已声明），这两次都会触发整页重渲染，重渲染时读到已经赋好的 `lay`。
   - 定性：**能跑，但靠副作用，不可依赖。** 游戏里如果 `lay` 在某个不伴随其他数据变更的时机更新，就会静默失效。
2. **样式双份真相。** `.hud { height: 40px }`、`.title { font-size: 16px }` 等 CSS 值与 `dv(40)`、`dv(16)` 重复。RW6 上两者恰好相等，所以看不出问题；换机型时 CSS 是错的，只有内联样式是对的。
3. **`this.scr` / `this.ui` 也未声明。** 它们只在 `showSum()` 里被读，赋值发生在 `onReady`，所以能用；但同样属于未声明属性。

#### v2.0 是否上过机：没有证据

| 证据 | 结论 |
|---|---|
| `docs/device-results-2026-10-24.md` 的读数全部是 v1.4（`CROWN t51 d-160 1st=-1`） | v2.0 无读数 |
| v1.4 产物中 grep 不到 `432 / W`、`layout W=` | v1.4 没有自适应排版 |
| v2.0 产物构建时间 2026-10-24T15:06:47Z（23:06 CST） | 晚于报告记录的 22:15 实测 |
| v1.4 归档包构建时间 14:49Z（22:49 CST） | 也晚于 22:15，归档包是否为当时安装的那一个无法证明 |

**结论**：仓库能证明"自适应排版代码编译通过"，不能证明"在 RW6 上显示正确"。M1 必须补这一条，而且要用一个"能看出差别"的测试（例如把 `hudH` 临时改成 120），不能只看默认界面——默认界面即使绑定失效也和 CSS 长得一样。

### 3.3 表冠：借 `scroll` 间接读取

源码位置：`index.ux:202-213`、`302-347`。

```html
<scroll id="crownScroll" class="probe" scroll-y="true"
        onscroll="onProbeScroll"
        ontouchstart="onProbeTouchStart"
        ontouchend="onProbeTouchEnd">
```

```js
onProbeScroll(e) {
  const y = (e && typeof e.scrollY === 'number') ? e.scrollY : 0
  const dy = y - this.scrollY
  this.scrollY = y
  if (!this.armed || this.touchActive || dy === 0) return
  if (this.basePending) { this.basePending = false; return }
  this.crownTicks++
  this.crownDelta += dy
  ...
}
```

#### 实测数据（转引 v1.4）

```
D7 CROWN up=0 down=-160 1st=-1 n=51
```

- 51 次事件，累计 −160 px → 约 **3.14 px/事件**；
- 首帧 `1st=-1` 被当作基线丢弃；
- **`up=0`**：四轮记录里没有任何正 `dy`。

#### 能得出什么

| 结论 | 等级 | 说明 |
|---|---|---|
| 表冠能驱动 `scroll`，应用能收到 `onscroll` | 实测 | 51 次事件 |
| 步长约 3.1 px/事件，事件很密 | 实测 | 160/51 |
| 只能拿到位移，拿不到角度/速度/按下/开始结束 | A + 实测 | 官方无 crown API |
| 正向 `dy` 是否存在 | **未验证** | 四轮全是负值；不能假设符号对称 |
| 表冠按压是否触发 `onBackPress` | **未验证/按不可用处理** | 3 轮有数据均为 N |
| 表冠能否驱动"被遮挡/窄条"滚动容器 | **未验证** | 探针用的是全宽滚动区 |

#### 源码里的三个隐患

1. **`readScrollY()` 是空操作**（345–347 行）：直接返回 `this.scrollY`，没有读元素真实位置。名字有误导性。
2. **`touchActive` 锁 700 ms**（309–315 行）：手指抬起后 700 ms 内的表冠输入全部丢弃。游戏里"点一下再转表冠"会明显掉输入。
3. **视图切换不重置基线**：`showSum()` 把 `mainOn=false`（399 行），`scroll` 节点被销毁；`closeSum()` 重建后滚动位置回到 0，但 `this.scrollY` 仍是旧值（例如 800），`armed` 仍为 true，`basePending` 仍为 false。下一次表冠事件会得到 `dy ≈ -800`，被记成一次巨大位移。
   - 这是**结构性 bug**，不是探针特有。任何"用 `if` 切走再切回"的界面都会踩到。
   - 修法：视图切换时 `scrollY = 0; basePending = true; inputLockUntil = now + 250`。

### 3.4 触摸

探针只绑了 `touchstart`/`touchend` 用来标记"手指是否在屏上"，实际按钮用的是 `onclick`。因此：

| 能力 | 状态 | 依据 |
|---|---|---|
| `click` 点击 | **实测可用**（操作者靠它跑完了全部测试） | 探针交互链路 |
| `touchstart` / `touchend` | 代码已绑，日志有触达 | 源码 + 交互链路 |
| `longpress` | 文档支持，**未单独实测** | A |
| `swipe` | 文档支持，**未单独实测**；且"滑动方向有滚动条时不触发" | A |
| 多点触控 | `Touch.identifier` 文档存在，**未实测** | A |
| `click` 与 `touchend` 是否同一次点击都触发 | **未实测** | 需要 M1 专项 |

**这是 RPG 输入框架最大的未知之一**：如果同一次点击同时触发 `click` 和 `touchend`，而两者都映射成 CONFIRM，对话就会一次跳两页。

`swipe` 与表冠的冲突是结构性的：

- 官方原文："组件上快速滑动后触发（滑动方向有滚动条时不触发该事件）"；
- 表冠又必须有一个可滚动容器；
- 如果为了表冠放一个全屏 `scroll`，地图上的 `swipe` 就可能永远不触发。

所以不能设计成"全屏滚动容器 + swipe 手势"。可选方案见 5.2。

| 项目 | 事实 | 影响 |

#### 存储 API 的硬约束（A 级，官方文档）

`@system.storage`：

```js
storage.get({ key, default, success(data), fail(data, code) })
storage.set({ key, value, success, fail })   // value 必须是 String
storage.delete({ key, success, fail })
storage.clear({ success, fail })
```

- **只能存字符串**；对象/数组必须自己 `JSON.stringify`；
- `value` 为空字符串会**删除**该项（不能把 `""` 当有效值）；
- `key` 不存在且未给 `default` 时，返回空字符串；
- 文档**没有写容量上限**，必须实测。

`@system.file`：

```js
file.readText({ uri, encoding, success({text}), fail })
file.writeText({ uri, text, encoding, append, success, fail })
file.readArrayBuffer({ uri, position, length, success({buffer}), fail })
file.writeArrayBuffer({ uri, buffer, position, append, success, fail })
file.move({ srcUri, dstUri, success(uri), fail })   // 可用于"临时文件→正式文件"
file.access / mkdir / rmdir / list / get / delete
```

- `readText` **支持应用资源路径**（如 `/Common/data/map01.json`），这是按需加载数据文件的正路；
- 写路径是 `internal://files/...`，临时区是 `internal://cache/...`；
- 失败码：202 参数错误、300 I/O 错误、301 文件不存在；
- 官方特别提示：小内存设备要及时清理无用文件，避免内存过载。

**推断（D）**：`writeText` 到 cache 再 `move` 到 files，可能是最接近"原子写"的存档方案（取决于底层是否 rename）。M1 要验证，不能假设。

## 5. D. 为 RPG 输入框架需要新增或修改的内容

### 5.1 输入抽象：先归一化，再分发

不要让页面直接处理 `click` / `onscroll`。所有原始事件先变成统一动作：

```js
// core/actions.js
const A = {
  UP: 'UP', DOWN: 'DOWN', LEFT: 'LEFT', RIGHT: 'RIGHT',
  CONFIRM: 'CONFIRM', CANCEL: 'CANCEL', MENU: 'MENU',
  PAGE_NEXT: 'PAGE_NEXT', PAUSE: 'PAUSE', DEBUG: 'DEBUG'
}
```

原始事件 → 动作的映射：

| 原始来源 | 归一化 | 备注 |
|---|---|---|
| 地图点击/滑动 | UP/DOWN/LEFT/RIGHT | 用 `touchstart`+`touchend` 自己算方向，不依赖 `swipe` |
| 对话/确认点击 | CONFIRM | **只绑 `click`**，不要同时绑 `touchend` |
| 菜单行点击 | CONFIRM(选中项) | 行本身是点击目标 |
| 表冠 scroll | UP/DOWN（仅菜单） | 累加阈值 + 冷却 |
| 屏幕左上角 | PAUSE | 软件按钮，永远可见 |
| 屏幕右上角 | MENU | 软件按钮 |
| `onBackPress` | CANCEL/PAUSE | 仅兜底，不作为唯一入口 |

**分发规则**（`core/input-router.js`）：

```
route(mode, action, now) -> action | null
```

- 每个模式有一张"接受哪些动作"的表；
- `now < lockUntil` 一律丢弃；
- `busy` 为 true（正在切图/存档/结算）一律丢弃；
- 同一个动作 120 ms 内只接受一次（去抖）；
- 模式切换后统一 `lockUntil = now + 200`。

这套东西是纯函数，能在 Node 里用表驱动测试，不依赖设备。

### 5.2 表冠方案：只在菜单用，不在地图用

**决策（建议）**：地图移动用触屏；表冠只用于菜单/列表/数值选择。

理由：

1. 表冠只能通过 `scroll` 读，地图如果也放滚动容器，会和滑动手势冲突（`swipe` 在有滚动条时不触发）。
2. 表冠方向符号未验证；地图移动对方向错误零容忍，菜单可以靠"翻到头就停"兜底。
3. 菜单本来就是列表，滚动容器是自然形态，不需要"隐藏轨道"这种未验证技巧。

菜单实现：

```html
<scroll id="menuScroll" scroll-y="true" onscroll="onMenuScroll">
  <div class="pad"></div>
  <div class="row" for="{{rows}}" onclick="onRowTap">
    <text class="{{$item.cls}}">{{$item.label}}</text>
  </div>
  <div class="pad"></div>
</scroll>
```

```js
onMenuScroll(e) {
  if (Date.now() < this.crownSuppressUntil) return
  const y = e.scrollY
  const idx = clamp(Math.round(y / ROW_H), 0, rows.length - 1)
  if (idx !== this.sel) { this.sel = idx; haptics.short() }
}
```

- 进入菜单：`scrollTo({top: sel*ROW_H, behavior:'instant'})`，并设 `crownSuppressUntil = now + 250`，避免程序化滚动被当成用户输入；
- 退出菜单：`scrollY = 0`、`sel` 保持不变、`crownSuppressUntil` 重置；
- 方向若相反：只改一个常量 `CROWN_SIGN = ±1`，不改逻辑。

**地图是否启用表冠**：M1 做一次"窄条测试"——右侧 80 px 放一个独立 `scroll`，其余区域是静态地图；只转表冠，看窄条是否收到 `onscroll`。如果收到，可作为可选辅助（上下移动）；收不到就永久关闭。不要先写进架构再验证。

### 5.3 触摸方案：点击与手势分离

- **点击**：只绑 `click`。不要再绑 `touchend` 做 CONFIRM。M1 要验证"一次点击是否只产生一次 `click`"。
- **滑动**：绑 `touchstart` 记起点，`touchend` 算 `dx/dy`；阈值 24 px，主轴判定（`|dx| > |dy| * 1.5` 才算水平）。不依赖 `swipe`，因为 `swipe` 会被滚动容器抑制。
- **方向输入**：地图支持两种——
  1. 点相邻格：`offsetX/offsetY` 换算成格子坐标，点玩家四周的格子即走一步；
  2. 滑动：一次滑动走一步，连续滑动需要重新起手（避免惯性误走）。
- **安全区**：底部 ≥ 56 px、左右 ≥ 16 px 不放关键按钮；确认/取消 ≥ 64×64；普通行 ≥ 48 px 高。
- **右滑退出风险**：如果系统把右边缘横滑当返回，地图横滑可能直接退出应用。M1 必须测"从右边缘向左滑"和"从左边缘向右滑"分别发生什么。若会退出，地图手势改为"点击相邻格"为主，横滑禁用。

### 5.4 页面与状态：单页 + 纯 JS 模块，不拆 `.ux` 组件

官方文档原文（自定义组件页）：

> 由于自定义组件拥有独立的 ViewModel，因此存在一定内存开销，在手表手环等轻量级设备上不建议使用。

所以：

- **不要**把地图/对话/菜单/战斗拆成 `.ux` 自定义组件；
- 用一个页面（`pages/Index`），内部用 `if` 切 `FIELD / DIALOG / MENU / BATTLE / SYSTEM / DEBUG`；
- 逻辑全部放 `src/core/*.js`，页面只做"读快照 → 绑数据 → 转发动作"；
- `core` 禁止出现 `@system.*`、`this.$element`、`setTimeout` 之外的平台 API；
- 这条约束要写成测试（见 5.7），否则几周后一定会破。

单页的代价是模板会变长（预计 800–1,500 行），但换来的是：没有页面栈、没有重复注册监听、没有页面重建导致的状态丢失。对 RPG 来说这笔账是划算的。

**路由**：只在"设置/关于"这类无状态页面考虑 `router.push`；游戏主流程不切页。M1 可选测一次 `router.push` + `router.back`，确认返回后模块级单例是否还在（这决定未来能不能用路由）。

### 5.5 软件返回/暂停：必须常驻

因为 `onBackPress` 不可依赖：

- 所有非 FIELD 界面左上角固定一个 `←`（CANCEL）；
- FIELD 界面左上角固定 `暂停`（PAUSE）；
- 暂停面板里提供"继续 / 存档 / 读档 / 回标题 / 退出"；
- "退出"要长按 600 ms + 二次确认，避免误触；
- 任何"只能靠返回键退出"的设计都视为缺陷。

### 5.6 存储：字符串 + 双槽 + 校验

```js
// core/save-codec.js
function encode(save) {
  const body = JSON.stringify(save)
  return JSON.stringify({
    v: 1,
    crc: crc32(body),
    body
  })
}
function decode(raw) {
  try {
    const env = JSON.parse(raw)
    if (env.v !== 1) return { ok: false, reason: 'version' }
    if (crc32(env.body) !== env.crc) return { ok: false, reason: 'crc' }
    return { ok: true, save: JSON.parse(env.body) }
  } catch (e) {
    return { ok: false, reason: 'json' }
  }
}
```

写入策略（A/B 双槽）：

```
load: 读 slotA、slotB，各自 decode；取 generation 更大且 crc 正确的一个
save: 写入"较旧"的那个槽；成功后 generation+1
```

这样即使写一半断电，另一个槽仍然可用。`storage` 是字符串键值，正好适合。

文件方案（备选，M1 验证）：

```
writeText -> internal://cache/save.tmp
file.move  -> internal://files/save.json
```

如果 `move` 是原子 rename，这比双槽更干净；如果只是 copy+delete，就没优势。

**必须实测的三件事**：

1. 单键能存多大（1 KB / 8 KB / 32 KB / 64 KB）；
2. 写入过程中杀应用，重启后能否读出旧值；
3. 损坏 JSON / CRC 错 / 版本号高，是否都能走恢复分支而不白屏。

### 5.7 调试：屏幕是唯一遥测通道

- 常驻一个 `DEBUG` 模式：最近 50 条日志、当前模式、坐标、步数、渲染耗时、存储测试结果；
- 关键结果压成一行 `CODE`（沿用探针的做法），方便拍照；
- `app.ux` 的 `onError` 把 `message + stack` 写入 `storage` 的 `crash` 键，下次启动显示"上次崩溃"页；
- 生产版用 `config.logLevel` 控制，不要把调试面板暴露给普通用户。

### 数据与版权闸门（必须在 M2 前决定）

- 不能把 ROM、原版图像、音乐、文本打进仓库或 RPK；
- 数值表（属性/伤害公式/掉落）是事实，风险较低；但**地图布局、NPC 对话、怪物名/道具名/描述**属于表达性内容，公开分发有侵权风险；
- 民间汉化文本是未授权衍生作品，不能直接拿来用；
- 如果目标是公开仓库/公开 RPK：需要原创美术、原创/授权文本，或只发引擎与工具、不发数据；
- 如果只是个人自用：把 ROM 转换器与导出数据放在 `.gitignore` 的 `data/local/`，仓库只提交格式说明与校验工具；
- ROM 必须用 CRC32/SHA-1 固化"地区 + 版本"，具体校验值需要你提供合法 ROM 后本地计算，我不会凭空写。
