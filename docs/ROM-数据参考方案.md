## 1. 目标 ROM 规格（已锁定）

| 项目 | 值 |
|---|---|
| 平台 | Super Famicom / SNES |
| 游戏 | Dragon Quest III: Soshite Densetsu e... |
| 地区 | Japan |
| 发售 | 1996-12-06 |
| 卡带容量 | 32 Mbit |
| ROM 大小 | 4,194,304 字节（无 copier header） |
| 数据库 | No-Intro |
| CRC32 | `13836bd2` |
| MD5 | `7c7c7db73b0608a184cc5e1d73d7695b` |
| SHA-1 | `b711341e4b1022d7645c5313840874aebc01b7b7` |
| SHA-256 | `dcf8fde55cec7095bc8b522820ffac65790a60054555f8665d54265d2ac36d8a` |

来源：`ButThouMust/dq6-sfc` README 的 DQ III SNES 小节，标注为 No-Intro 规格。这是目前能拿到的最明确、可复核的版本锚点。

补充（2026-10-25）：用户提供的一张 ROM 信息页截图显示 `CRC 13836bd2`、Region Japan、Version 1.0、Cart size 32 Mbit，与 No-Intro 目标一致。截图里的 `2.25 MB` 是下载/压缩体积，不是 ROM 本体；32 Mbit 卡带的 `.sfc` 应为 4,194,304 字节。**仍需 SHA-1 最终确认。**

### 1.1 必须排除的版本

| 版本 | 为什么不行 |
|---|---|
| 英文汉化补丁版 | 文本指针、字库、部分菜单被改，偏移不可复用 |
| GBC 版 | 完全不同的数据格式 |
| HD-2D 重制版 | 完全不同的数据与数值 |
| 美版 NES / 其他地区 | 不是 SFC 日版 |
| 打了任何 IPS/BPS 补丁的 ROM | 同上，哈希对不上 |

**判定标准只有一个：`identify.mjs` 的 SHA-1 匹配。** 不匹配就不要往下走。

### 1.2 copier header

- 有些 `.smc` 带 512 字节 copier header；
- 本工具会检测 `size % 1024 === 512` 并自动去掉；
- No-Intro 哈希针对**去头 ROM**；工具同时给出原始文件与去头 ROM 的哈希。

## 2. 合法边界

| 对象 | 可以做 | 不可以做 |
|---|---|---|
| ROM 文件 | 本地只读、算哈希、提取数据 | 提交、上传、放进 RPK、分享 |
| 原版文本 | 本地阅读，作为"语义参考" | 直接打包、逐句翻译后冒充原创 |
| 原版图像/音乐 | 本地看，作为风格参考 | 提取进 RPK、重绘后当原创 |
| 地图拓扑/碰撞 | 本地提取，转成自己的数据格式 | 公开分发原版地图数据（有版权风险） |
| 数值表 | 本地提取，做一致性校验 | 在公开仓库里打包整套原作数据 |
| 工具/格式说明 | 开源、公开 | 附带 ROM 或提取出的原版素材 |

### 2.1 两种发布形态

**A. 个人自用（默认假设）**

- ROM 放 `data/local/dq3.sfc`（`.gitignore`）；
- 提取数据放 `data/local/`；
- RPK 本地构建，本地安装；
- 仓库只提交代码、工具、schema、占位数据。

**B. 公开仓库 / 公开 RPK**

- 仓库不含 ROM、不含提取出的原版文本/图像/音乐；
- 公开 RPK 使用原创中文文本 + 原创图形；
- 地图拓扑与数值表是否公开，需要单独评估（建议不公开整套）；
- 标题"勇者斗恶龙"是商标，公开版需要改名；
- 最稳的做法：公开"引擎 + 转换器 + 占位数据"，用户用自己的 ROM 在本地生成数据包。

**这两种形态的代码是同一套，差别只在 `data/` 目录是否随包发布。**

## 3. `ButThouMust/dq6-sfc` 审计结果

| 项目 | 事实 |
|---|---|
| 仓库 | `ButThouMust/dq6-sfc` |
| 描述 | Font and script dumpers for Dragon Quest VI and III for Super Famicom |
| 语言 | Java |
| 文件 | 2 个 ScriptDumper、2 个 FontDumper、1 个 Huffman 生成器、2 个 `.tbl` 表、DQ6 ROM layout 笔记 |
| LICENSE | **没有**；GitHub API 的 `license` 为 `null` |
| 覆盖 | 字体、对话框文本（Huffman 压缩）、脚本指针 |
| 不覆盖 | 菜单文本、角色默认名、道具/武器/防具名、除"字符串结束/换行"外的控制码 |
| DQ3 支持 | 作者发现 DQ3 SFC 复用了 DQ6 的字体与对话脚本系统，只是指针位置不同；提供了 DQ3 版本 |
| 表文件来源 | 作者注明来自 byuu 的 abandoned tools（RHDN 存档），许可同样不明确 |

### 3.1 结论

1. **不能用它的代码或 `.tbl` 直接进本项目**——没有许可证，默认保留所有权利。
2. 可以把它当作**格式研究资料**：确认 DQ3 文本是 Huffman 压缩、与 DQ6 同源、指针不同。
3. 它**不提供**怪物、道具、咒文、成长、地图、事件——这些要自己提。
4. 如果要用它的表/代码，正确做法是联系作者拿许可；拿不到就自己写 dumper。
5. 对公开版来说，文本本来就要重写，所以它的价值主要是"知道格式"，不是"拿文本"。

## 4. ROM 能提供什么、不能提供什么

| 数据 | ROM 里有没有 | 提取难度 | 备注 |
|---|---|---|---|
| 怪物属性（155 种） | 有 | 中 | 固定长度记录 + 指针表；可用 RAM 交叉验证 |
| 道具/装备属性/价格 | 有 | 中 | 记录长度与字段需定位 |
| 咒文（约 60 个） | 有 | 中 | MP/效果/学习表分开 |
| 成长区间 | 有 | 中 | 每职业每级 min/max |
| 遭遇表 | 有 | 中 | 区域 → 怪物组 |
| 地图拓扑/碰撞 | 有 | 高 | 压缩 tilemap + 碰撞位图 |
| NPC 位置/日程 | 有 | 高 | 对象表 + 脚本 |
| 事件/flag | 有 | 很高 | 自定义脚本 VM；需 RAM diff |
| 对话文本 | 有 | 高 | Huffman；dq6-sfc 有格式笔记 |
| 伤害/命中公式 | **没有** | — | 只能从运行结果采样拟合 |
| 敌人 AI 权重 | 部分 | 高 | 可能是脚本/表；需观察 |
| 原版图像/音乐 | 有 | 高 | **不提取进 RPK** |

**关键认知**：ROM 是"数据源"，不是"公式源"。伤害公式、AI 决策、部分随机规则必须从运行时行为采样，不能指望在 ROM 里找到一行 `damage = atk - def/2`。

## 5. 三种提取方法

### A. ROM 静态分析

- 找指针表 → 找记录 → 按字段解析；
- 适合：怪物、道具、咒文、成长、遭遇、地图；
- 优点：完整、可复现、一次提取全表；
- 缺点：需要先定位表；压缩/指针/变长记录会增加难度；
- 工具：Node 脚本 + hex 查看（ImHex/010 Editor 均可，非必需）。

### B. 模拟器 RAM 追踪

- 在 BizHawk / bsnes-plus 里跑游戏，搜索内存值，改值验证；
- 适合：队伍结构、金币、位置、flag、RNG、当前地图；
- 优点：直接得到"运行时数据模型"，不依赖 ROM 格式；
- 缺点：需要手动操作；不同版本地址可能不同；
- 工具：BizHawk Lua（`memory.read_u8/u16`、savestate、`memory.write_u8`）。

### C. 运行时观察

- 固定属性，记录 20–50 次伤害/命中/逃跑/掉落；
- 适合：公式、概率、AI 倾向；
- 优点：最接近真实行为；
- 缺点：慢；需要大量样本；模拟器准确性影响结果；
- 工具：Lua 自动脚本 + CSV 记录 + 拟合脚本。

**三者必须交叉验证**：ROM 表说史莱姆 HP=8，RAM 里打一场看到 8，才算确认。

## 8. RAM 追踪怎么做（具体）

### 8.1 队伍结构

1. BizHawk 打开 ROM，新建游戏；
2. 记录初始：金币、等级、HP、MP、力量等；
3. 用 Cheat Search 搜金币（0 → 打一场 → 变化）；
4. 找到金币地址后，按记录长度向周围扫描；
5. 候选结构：`name[?] + level + exp + hp + mp + str + agi + res + int + luck + ...`；
6. 改一个字节，看游戏里哪个数值变化 → 确认字段偏移；
7. 四个角色重复，确认步长；
8. 输出 `party-struct.json`：字段名、偏移、类型、字节序。

### 8.2 位置与地图

1. 站在城里，搜 X/Y；
2. 走一格，再搜变化；
3. 确认地图 id、X、Y、朝向；
4. 切地图，看地图 id 变化；
5. 记录地图 id → 名称映射（手动，垂直切片先做 4 张）。

### 8.3 Flags

1. 存档状态 A（事件前）；
2. 触发事件；
3. 存档状态 B；
4. diff 两块 RAM，找 0→1 的字节；
5. 逐个改回 0，看事件是否回退；
6. 确认后命名 flag（如 `met_king`）。

### 8.4 战斗采样

1. Lua 脚本固定队伍属性（写入 RAM）；
2. 进入战斗，记录敌方 HP；
3. 执行普通攻击，读伤害；
4. 重复 50 次，输出 CSV：`atk, def, damage, crit, hit`；
5. 换属性组合，重复；
6. 用 `tools/calibrate.mjs` 拟合。

**注意**：改 RAM 可能触发校验/崩溃；每次只改一个字段，改完立刻存档状态，失败就回滚。

## 9. 地图提取怎么做

### 9.1 两条路

| 方法 | 优点 | 缺点 |
|---|---|---|
| VRAM tilemap 快照 | 不依赖 ROM 格式；所见即所得 | 只能拿到当前屏幕；需要拼接 |
| ROM tilemap 数据 | 完整、可批量 | 需要定位地图表/压缩格式 |

**垂直切片先用 VRAM 快照**：

1. 在 BizHawk 的 Tile Viewer / VRAM Viewer 里看 BG tilemap；
2. 导出 32×32 或 64×64 的 tile 索引；
3. 用模拟器逐屏走，拼成完整地图；
4. 碰撞：用 RAM 的 X/Y + 尝试走，逐格记录可走/不可走；
5. 产出：`map.json`（tile 索引 + 碰撞位图 + 对象表）；
6. 用自己的渲染器复现，逐格对比。

### 9.2 只存"结构"，不存"原图"

- 存 tile 索引/碰撞/对象，不存原版 tile 图像；
- 渲染时用自己的地形图标/色块；
- 这样既保留拓扑，又不把原版美术打包。

## 10. 文本提取怎么做

### 10.1 已知

- DQ3 SFC 对话文本是 **Huffman 压缩**；
- 与 DQ6 同源，指针不同；
- `dq6-sfc` 有格式笔记和 dumper，但**无许可证**；
- 菜单/道具/怪物名不在它的覆盖范围。

### 10.2 三条路

| 方案 | 可行性 | 风险 |
|---|---|---|
| 本地用 `dq6-sfc` 跑一遍，只做研究 | 高 | 不能把代码/表/文本进仓库 |
| 联系作者拿许可 | 中 | 等待；不一定同意 |
| 自己写 dumper（按格式笔记） | 中 | 需要 Huffman 表；表来源许可不清 |

### 10.3 建议

1. 先在本地用 `dq6-sfc` 验证"能不能 dump 出可读文本"——只作为研究，不提交；
2. 同时联系作者，说明用途，询问是否可以 MIT/CC 授权；
3. 如果拿不到许可，就自己实现 Huffman 解码（格式公开可研究），表自己从 ROM 统计/推导；
4. **公开版本来就要原创中文**，所以文本提取的优先级低于数值/地图；
5. 原版文本只用于"语义对照"，不进入发布包。

## 11. 公式校准怎么做

ROM 里没有公式，只有行为。步骤：

1. 用 Lua 固定攻击方/防守方属性；
2. 记录 50 次普通攻击的伤害（含未命中/暴击）；
3. 记录 20 次咒文伤害（不同智力/抗性）；
4. 记录 20 次回复量；
5. 记录 20 次逃跑结果；
6. 输出 CSV；
7. 用 `tools/calibrate.mjs` 拟合候选公式的参数；
8. 把拟合结果写进 `data/release/formulas.json`；
9. 用固定 RNG 种子写 golden test；
10. 在游戏内跑 100 场模拟战斗，对比分布。

**没有 50 组以上样本，不要写"已还原公式"。**

## 12. 数据清单与可复现性

`data.manifest.json` 必须包含：

```json
{
  "source": {
    "name": "Dragon Quest III: Soshite Densetsu e... (Japan)",
    "crc32": "13836bd2",
    "sha1": "b711341e4b1022d7645c5313840874aebc01b7b7",
    "sha256": "dcf8fde55cec7095bc8b522820ffac65790a60054555f8665d54265d2ac36d8a"
  },
  "extractor": "0.1.0",
  "generatedAt": "2026-10-25T00:00:00Z",
  "tables": {
    "monsters": { "rows": 155, "sha1": "..." },
    "items": { "rows": 0, "sha1": "..." },
    "spells": { "rows": 60, "sha1": "..." }
  }
}
```

规则：

- 同一 ROM + 同一提取器 → 同一哈希；
- 行数不对 → 构建失败；
- 引用不存在 → 构建失败；
- 任何表标 `unverified` 的，不允许在验收里写"通过"。

5. 确认：**个人自用** 还是 **公开仓库/公开 RPK**；
6. 可选，但能大幅加速：
   - 一个"刚进阿利亚罕城"的 BizHawk 存档状态；
   - 一个"第一场战斗"的存档状态；
   - 10–20 组固定属性的伤害截图/数值。

### 13.3 如果哈希不匹配

- 不要继续提取；
- 先确认地区/版本/是否打了补丁；
- 如果只有别的版本，告诉我具体哈希，我评估是否另开一套偏移表（工作量会明显增加）。

## 14. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| ROM 版本不对 | 所有偏移错 | `identify.mjs` 强制校验 |
| 汉化补丁 | 文本/菜单偏移变 | 只用原版日文 ROM 做结构 |
| 压缩/脚本格式未知 | 地图/事件提取慢 | 先 RAM 追踪，后 ROM 静态 |
| `dq6-sfc` 无许可 | 不能复用代码/表 | 自写或联系作者 |
| 地图/文本版权 | 公开分发风险 | 公开版只发工具 + 原创数据 |
| 公式样本不足 | "还原"不可信 | 50 组以上 + 分布检验 |
| 模拟器不准确 | 采样偏差 | 用高精度模拟器；关键值用实机/多模拟器交叉 |
| 数据量/内存 | 加载失败 | 分文件、按需加载；M1 先测 |
| 时间 | 全量提取很长 | 先垂直切片，再铺量 |
