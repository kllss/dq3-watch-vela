# 地图移动与右滑规避方案

- 适用：REDMI Watch 6 / Vela JS 应用 / 432×514
- 目标：地图移动要跟手、可预期；右滑系统返回不能把玩家踢出游戏
- 前置：`docs/GDD-v0.1.md`、`docs/UI-SPEC-v0.1.md`、`docs/M0-仓库审计报告.md`
- 日期：2026-10-25

---

## 0. 先把问题拆成两件事

1. **动态地图移动**：玩家走一步，视野怎么跟着变；是整屏重绘、相机平移，还是做平滑滚动。
2. **规避右滑系统返回**：Vela 应用拿不到 `onBackPress`，也不能关掉系统手势；怎么让玩家在操作地图时不会误触退出。

这两件事必须一起设计，因为**最可靠的右滑规避方式，就是不让地图依赖横向滑动**。

---

## 1. 约束（按 M0 实测）

| 约束 | 影响 |
|---|---|
| `onBackPress` 3 轮有数据均未触发 | 不能拦截返回；不能把暂停/退出交给系统手势 |
| 无公开 API 关闭系统手势 | 不能"禁用右滑" |
| 无 canvas | 地图只能用 `div`/`text` 拼格 |
| Vela 只支持 flex，不支持 grid/gap | 地图要 9 个 row div × 11 个 tile div |
| 无 `transform` / `transition` 保证 | 不做依赖动画的平滑相机 |
| 表冠只能读 `scroll` 位移 | 地图不用表冠 |
| 触摸事件可能 `click` + `touchend` 双触发 | 只用一种确认事件 |

---

## 2. 结论（推荐方案）

| 问题 | 方案 |
|---|---|
| 地图移动 | **离散步进 + 相机跟随**：走一格，重算 11×9 视口；玩家居中，地图边缘夹取 |
| 主操作 | **点相邻格**：精确、无手势冲突、不会触发系统返回 |
| 副操作 | **中心区域竖向拖动**：上下移动；横向移动仍用点按 |
| 横向滑动 | **永久禁用**：右滑返回在深度 1/2 都关不掉（见 7.0） |
| 平滑滚动 | **v0.1 不做**；M4 性能允许后再评估 2 帧滑动 |
| 暂停/返回 | 屏幕左上角软件按钮，永不依赖系统手势 |

一句话：**把"移动"从"滑动手势"降级成"点格子"，右滑问题就消失了一大半。**

---

## 3. 地图模型

### 3.1 数据结构

```js
map = {
  id: 'aliahan_field',
  w: 32,
  h: 24,
  tiles: Uint8Array,        // 32*24，tile id
  collision: Uint8Array,    // 每格 1 字节位掩码：0x01 步行可走，0x02 船可走，0x04 神鸟可走
  objects: new Map(),       // key "x,y" -> {type:'npc'|'door'|'chest'|'sign', ...}
  encounters: null | { rate: 1/16, groups: [...] },
  indoor: false
}
```

- `tiles` 用 `Uint8Array`，32×24 = 768 字节，加载和遍历都便宜。
- `objects` 用字符串 key，查找 O(1)；地图加载时构建。
- `collision` 用位掩码，支持不同载具（步行/船/神鸟）共用一张图。

### 3.2 相机

```js
const VIEW_W = 11
const VIEW_H = 9
const CENTER_X = 5   // (11-1)/2
const CENTER_Y = 4   // (9-1)/2

function cameraFor(map, player) {
  const maxX = Math.max(0, map.w - VIEW_W)
  const maxY = Math.max(0, map.h - VIEW_H)
  return {
    x: clamp(player.x - CENTER_X, 0, maxX),
    y: clamp(player.y - CENTER_Y, 0, maxY)
  }
}
```

- 玩家在视口中心 `(5,4)`；
- 到地图边缘时相机夹取，玩家自然偏离中心；
- 不做"相机缓动"，避免每帧重算。

### 3.3 视口生成

```js
function buildRows(map, cam, player, npcs) {
  const rows = []
  for (let vy = 0; vy < VIEW_H; vy++) {
    const cells = []
    for (let vx = 0; vx < VIEW_W; vx++) {
      const x = cam.x + vx
      const y = cam.y + vy
      const tile = map.tiles[y * map.w + x]
      let ch = TILE_CH[tile]
      let cls = TILE_CLS[tile]

      if (player.x === x && player.y === y) {
        ch = '@'; cls = 'player'
      } else if (npcs.has(`${x},${y}`)) {
        ch = 'K'; cls = 'npc'
      }
      cells.push({ ch, cls })
    }
    rows.push({ cells })
  }
  return rows
}
```

Vela 模板（嵌套 `for`，M1 必须实测）：

```html
<div class="map">
  <div class="map-row" for="{{rows}}">
    <div class="tile {{$item.cls}}" for="{{$item.cells}}">
      <text class="tile-t">{{$item.ch}}</text>
    </div>
  </div>
</div>
```

```css
.map { width:396px; height:324px; flex-direction:column; }
.map-row { width:396px; height:36px; flex-direction:row; }
.tile { width:36px; height:36px; justify-content:center; align-items:center; }
```

> 如果 Vela 不支持嵌套 `for`：把 9 行写成 9 个显式 `map-row`，每行 11 个 `tile`；或者把 99 格拍平成 9 个数组，用 9 个独立 `for`。不要用自定义组件绕过。

## 4. 移动管线

### 4.1 一步的完整顺序

```
输入（点格/拖动/方向键）
 → 输入锁/忙碌检查
 → 目标格越界/碰撞/NPC 检查
 → 更新玩家坐标
 → 重算相机
 → 触发地块对象（门/楼梯/宝箱/告示）
 → 随机遭遇检查（若没有触发对象）
 → 重建 11×9 视口
 → commit（页面赋值）
 → 设置 120ms 步进冷却
```

顺序很重要：

- **先判定再移动**，避免"卡进墙里再退回"；
- **门/楼梯优先于遭遇**，避免在门口被战斗打断；
- **遭遇放在移动后**，符合 DQ 的"走一步才可能遇敌"；
- **commit 只做一次**，避免一次移动触发多次重绘。

### 4.2 核心代码

```js
function tryMove(game, dx, dy, now) {
  if (game.busy || now < game.inputLockUntil) {
    return { ok: false, reason: 'locked' }
  }

  const nx = game.player.x + dx
  const ny = game.player.y + dy

  if (nx < 0 || ny < 0 || nx >= game.map.w || ny >= game.map.h) {
    return { ok: false, reason: 'bounds' }
  }
  if (!(game.map.collision[ny * game.map.w + nx] & game.vehicleMask)) {
    return { ok: false, reason: 'wall' }
  }
  if (game.npcs.has(`${nx},${ny}`)) {
    return { ok: false, reason: 'npc' }
  }

  game.player.x = nx
  game.player.y = ny
  game.steps++
  game.safeSteps = Math.max(0, game.safeSteps - 1)
  game.camera = cameraFor(game.map, game.player)

  const obj = game.map.objects.get(`${nx},${ny}`)
  if (obj && obj.type === 'door') {
    return { ok: true, transition: obj }   // 由上层 enterMap
  }
  if (obj && obj.type === 'chest' && !game.flags.has(obj.flag)) {
    return { ok: true, chest: obj }
  }
  if (obj && obj.type === 'sign') {
    return { ok: true, dialog: obj.textKey }
  }

  if (game.map.encounters && game.safeSteps === 0) {
    if (game.rng() < game.map.encounters.rate) {
      return { ok: true, encounter: true }
    }
  }

  game.rows = buildRows(game.map, game.camera, game.player, game.npcs)
  game.inputLockUntil = now + 120
  return { ok: true }
}
```

### 4.3 连走 / 长按

- 点相邻格：一次一步，天然不会连走。
- 拖动：每跨过 24px 发一步，然后把起点重置到当前位置；松手停止。
- 方向键盘（可选）：按下 300ms 后，每 220ms 重复一步；松手取消。
- 不做惯性；松手立刻停。

### 4.4 地图切换

```js
async function enterMap(game, mapId, x, y) {
  game.busy = true
  game.inputLockUntil = now() + 250
  const map = await loadMap(mapId)     // file.readText + JSON.parse
  game.map = map
  game.player = { x, y }
  game.camera = cameraFor(map, game.player)
  game.rows = buildRows(map, game.camera, game.player, game.npcs)
  game.busy = false
}
```

- 切图期间 `busy=true`，所有输入丢弃；
- 加载失败 → 显示"地图读取失败"，回到上一个地图，不白屏；
- 不做淡入淡出；瞬时切换最稳。

## 5. 渲染与性能

| 项目 | 预算 |
|---|---|
| 视口 | 11×9 = 99 个 tile |
| 每步重建 | 99 个小对象 + 9 个行对象 |
| 目标耗时 | < 50ms/步（M1 T13） |
| 渲染频率 | 只在移动/切图时；不做 60fps |
| 地图缓存 | 当前 + 上一张，最多 2 张 |
| 数据加载 | `file.readText('/Common/data/maps/xxx.json')`，按需 |

避免：

- 不要用 `setInterval` 每 16ms 重算视口；
- 不要每步重建整张地图对象；
- 不要把 99 个 tile 写成 99 个独立 setter；
- 不要在模板里做坐标计算。

## 6. 平滑移动：做还是不做

### 6.1 方案 A：离散步进（推荐）

- 走一步，整屏换一次；
- 玩家永远在中心（边缘除外）；
- 视觉上是"格子跳一下"，但响应快、成本低；
- DQ3 本来就是格子移动，玩家不会觉得违和。

### 6.2 方案 B：两帧滑动（可选，M4 再评估）

- 渲染 12×10 的窗口，放在 396×324 视口里；
- 走一步时，把地图层按 36px 偏移，分 2–3 帧回正；
- 需要 `position:absolute` + 负偏移 + `overflow:hidden`；
- 风险：Vela 的裁剪/负偏移/定时器帧率未验证；143 个节点比 99 个贵；
- 结论：**v0.1 不做**；M4 有性能数据后再决定。

### 6.3 方案 C：只做"落点反馈"

- 玩家格闪一下/目的地格亮一下；
- 不移动相机层，只重绘视口；
- 成本最低，适合手表。

> 建议：A + C。先保证"每一步都对"，再谈"看起来顺滑"。

## 7. 右滑系统返回：能做什么、不能做什么

### 7.0 先试一个可能的开关：`followHand`

vivo 手表快应用文档里有一个页面级字段：

```json
"router": {
  "pages": {
    "pages/Index": {
      "component": "index",
      "followHand": "disable"
    }
  }
}
```

含义：关闭页面的"右滑跟手/返回"。

但要注意：

- 小米 Vela 的 manifest 文档只列了 `component` / `path` / `launchMode`，**没有 `followHand`**；
- 本机 `aiot-toolkit@2.0.5` 的源码里搜不到这个字段，但**编译器不报错，并把它原样保留进了 RPK 的 manifest.json**（见下方编译级验证）；
- 运行期是否生效仍然未知。

所以它是"**值得先试，但不能依赖**"的开关：

| 结果 | 行动 |
|---|---|
| 编译通过 + 真机右滑不返回 | 最干净，直接用 |
| 编译通过但无效果 | 回到"点相邻格 + 不横滑" |
| 编译报错/字段被拒 | 删掉，按交互方案做 |

**编译级已验证（2026-10-25）**：

- 用现有 probe 工程加 `followHand: "disable"`，`aiot-toolkit@2.0.5` 构建成功；
- 解包 RPK，`manifest.json` 里仍保留该字段；
- 结论：**编译器接受并透传**；运行期未知。

**真机第一轮（2026-10-25，用户实测）**：`data/local/probe-followhand-disable.rpk`，包名 `com.probe.followhand`，应用名"右滑测试"。

- 结果：**横滑不返回、不退出**。
- 但这个包是**单页应用**（`router` 只有一个页面），而右滑返回的语义是"弹出页面栈的上一层"。栈深度为 1 时，系统本来就没有可返回的页面。
- 所以这一轮只能证明：**在栈深度 1 时，横滑不会退出应用**。它**不能**证明 `followHand` 生效，也不能证明深度 2 时横滑不会返回。

**对照实验（2026-10-25 已完成，G0 判定：`followHand` 无效）**

两个包除"B 页是否带 `followHand`"外完全相同：

| 包 | 包名 | 应用名 | 图标 | 页面栈 | B 页 `followHand` |
|---|---|---|---|---|---|
| `data/local/glab-1-control.rpk` | `com.klls.glab.ctrl` | 对照 | 蓝色右箭头 | A → B（深度 2） | 无 |
| `data/local/glab-2-followhand.rpk` | `com.klls.glab.fh` | 关跟手 | 橙色禁止符 | A → B（深度 2） | `disable` |

两个包都是 17 KB 左右，两页；功能差异只在 `manifest.json` 的该字段与 B 页顶部一行标签。图标与名称不同只是为了在表盘上分得清——颜色（蓝/橙）和轮廓（箭头/禁止符）都不同，40px 下仍可辨认。B 页会显示：`touchstart` / `touchend` 次数、最后一滑 `dx/dy`、`onBackPress` 次数、页面栈深度。A 页显示 `onShow` / `onHide` / `onBackPress` 次数。

测试步骤（两个包各做一遍）：

1. 打开应用 → 点「进入 B 页」；
2. 确认 B 页"栈深度 = 2"；
3. 在绿色测试区**中间**向右滑 5 次（每次都要滑过 80px 以上）；
4. 在绿色测试区**最左边缘**（手指从屏幕最左起手）向右滑 5 次；
5. 记录：是否回到 A 页 / 是否退回表盘 / 是否毫无反应；B 页的 `touchstart`、`touchend`、`dx`、`onBackPress` 读数。

判读表（事后对照用）：

| 对照组（无字段） | 实验组（disable） | 结论 | 后续 |
|---|---|---|---|
| 回到 A 或退回表盘 | 留在 B | **`followHand` 生效** | 全应用页面都加该字段，横滑可安全启用 |
| 回到 A 或退回表盘 | 也回到 A / 也退出 | **字段被忽略** ← 实测结果 | 横滑永久关闭，见 7.3 |
| 都没反应 | 都没反应 | RW6 的 JS 应用没有右滑返回 | 横滑无风险，但仍保留软件返回按钮 |

**实测结果（2026-10-25）：两个包都会返回。**

- 对照组（无字段）右滑 → 返回；
- 实验组（`followHand: "disable"`）右滑 → **同样返回**。

判定：**在栈深度 2 上，这个字段不阻止"弹回上一页"。** 注意限定条件——这一步是页面栈行为。

**栈底的补充实测（决定性）**

一度以为字段在栈底有用（第一轮探针"没退出"），但严格 A/B 否掉了这个解释：

| 场景 | 结果 |
|---|---|
| 深度 1 + 无字段 | **退出应用** |
| 深度 1 + `followHand: disable` | **照样退出应用** |

两个包 `pages/Game/index.js` 字节一致，只有 manifest 差一个字段。所以：

> **`followHand` 在深度 1 和 2 都无效。右滑返回无法用应用层手段关闭。**

第一轮探针的"没退出"判为手势没被系统识别（probe 页面中部有滚动容器），该条记录作废。

对项目的准确结论：

1. **只要栈深度 ≥ 2，横滑就会被系统吃掉** → 地图横向仍然只能点格（见 7.3）；
2. **单页 = 栈底 = 一滑就退出**，所以游戏不能只有一个页面；
3. 唯一的结构性缓解是在游戏页下面垫一层（见 7.6），但它只买到一次缓冲；
4. **自动存档仍然是必需的**——崩溃、低电、系统回收、以及第二次右滑，都会结束进程。

**还需要补两个读数**（决定横向手势是否还有任何可用空间）：

| 问题 | 为什么要问 | 怎么读 |
|---|---|---|
| 中间右滑也会返回，还是只有贴左边缘才会？ | 若只有边缘返回，中心区域的横滑仍可用 | B 页从 x≈200 起手滑 5 次 |
| 返回瞬间 B 页 `onBackPress` 有没有加 1？ | 若加 1，说明能拿到回调，未来仍可能拦截 | 看 B 页 `onBackPress` 计数 |

补充读数（同样有价值）：

- `touchend` 次数 < `touchstart` 次数 → 手势被系统中途抢走；
- `dx` 明显小于实际滑动距离 → 触摸坐标被系统截断；
- `onBackPress` 有值 → 说明返回键/手势会走应用回调，可以拦截（与 M0 的结论冲突，需要复核）。

### 7.1 不能做的

| 做法 | 为什么不行 |
|---|---|
| `onBackPress` 里 `return true` | RW6 3 轮实测未触发 |
| `preventDefault()` | 系统手势在 OS 层，Vela 触摸事件拦不住 |
| manifest/display 关闭手势 | 小米 Vela 文档没有；vivo 的 `followHand` **在深度 1/2 实测均无效**（见 7.0） |
| 透明遮罩挡边缘 | 遮罩只能挡应用内事件，挡不住系统手势 |
| 全屏 `scroll` 吃掉横滑 | 可能吃掉应用内拖动，但系统手势优先级更高，未验证 |

### 7.2 能做的

| 做法 | 可靠性 | 说明 |
|---|---|---|
| **点相邻格移动** | 最高 | 完全不产生横向手势 |
| **中心区域竖向拖动** | 高 | 系统返回通常从左边缘起手；中心拖动不碰它 |
| **左边缘 72px 排除区** | 中高 | 起手点落在排除区：**点按仍可走，拖动不响应**。注意：它防的是"误操作"，不是"返回"——返回拦不住 |
| **横向滑动默认禁用** | 最高 | 没有横滑，就没有误触，也不触发返回 |
| **软件暂停/返回** | 最高 | 不依赖系统手势 |
| **可选方向键盘** | 高 | 4 个按钮，完全无手势 |
| **关键节点自动存档** | 最高 | 右滑可能直接退出应用，这是唯一的数据保险 |

### 7.3 推荐交互

**地图层面的结论没变：只要栈深度 ≥ 2 横滑就会被系统吃掉，所以地图只有一个方案，没有分支。**

（`followHand` 在两个深度都无效，这不是地图层的问题，见 7.0 / 7.6。）

```
主操作：点相邻格（上/下/左/右都能点）
副操作：在地图中心区域上下拖动（只竖向）
横向：只点，不滑
边缘：左 72px / 右 24px / 上 56px / 下 56px 不响应拖动
暂停：左上角软件按钮
```

这样：

- 玩家不需要学习"从哪边滑"；
- 不产生任何横向手势，也就不会触发系统返回；
- 边缘区域不参与移动，玩家不会"以为在走位、实际被弹走"。

**曾经考虑过的"放开横滑"分支，已作废**

原计划里有一个 `SWIPE_BACK_SAFE` 构建期常量：如果 G0 证明右滑返回不存在、或 `followHand` 生效，就打开中心区域的横滑。现在 G0 结论是"会返回、且关不掉"，这个常量**不引入**，避免以后有人误开。

**新增：把"被返回"当成常态来设计**

既然右滑拦不住，游戏必须假设"玩家随时可能被系统弹出去"：

- 游戏是单页应用，右滑退出 = 应用被关闭，内存里的进度全部丢失；
- 所以**自动存档必须在关键节点写盘**：换地图、战斗结束、商店交易、升级、拿到关键道具；
- `onHide` / `onDestroy` 里也要尝试写一次（是否来得及未验证，不能只依赖它）；
- 重启后从自动存档恢复，位置回到"最近的安全点"（地图入口或最近城镇），而不是精确坐标——精确坐标可能落在战斗中或事件中途；
- onHide 到底来不来得及写盘，用平台研究仓库的 [`experiments/storage-probe/`](https://github.com/kllss/redmi-watch-6-vela-input/tree/main/experiments/storage-probe)（安装包 `releases/storage-probe.rpk`）实测，判读表见该目录 README。

### 7.4 手势识别代码

```js
const SAFE = { left: 72, top: 56, right: 432 - 24, bottom: 514 - 56 }
const DRAG_STEP = 24

const g = {
  active: false,
  blocked: null,
  x: 0, y: 0,
  lastX: 0, lastY: 0
}

function onTouchStart(e) {
  const t = e.touches[0] || e.changedTouches[0]
  const x = t.clientX
  const y = t.clientY

  if (x < SAFE.left || x > SAFE.right || y < SAFE.top || y > SAFE.bottom) {
    g.active = false
    g.blocked = 'edge'      // 交给系统；应用不响应
    return
  }
  g.active = true
  g.blocked = null
  g.x = g.lastX = x
  g.y = g.lastY = y
}

function onTouchMove(e) {
  if (!g.active) return
  const t = e.touches[0] || e.changedTouches[0]
  const dx = t.clientX - g.lastX
  const dy = t.clientY - g.lastY
  if (Math.abs(dx) < DRAG_STEP && Math.abs(dy) < DRAG_STEP) return

  // 只认竖向；横向留给"点相邻格"
  if (Math.abs(dy) >= Math.abs(dx)) {
    step(dy > 0 ? 1 : -1, 0)   // down / up
  } else {
    // 默认不响应；如果 M1 证明横滑安全，再打开
    // step(dx > 0 ? 1 : -1, 0)
  }
  g.lastX = t.clientX
  g.lastY = t.clientY
}

function onTouchEnd() {
  g.active = false
}
```

### 7.5 点相邻格

```js
function onMapTap(e) {
  const t = e.changedTouches ? e.changedTouches[0] : e
  const rect = mapEl.getBoundingClientRect()
  const vx = Math.floor((t.clientX - rect.left) / 36)
  const vy = Math.floor((t.clientY - rect.top) / 36)
  if (vx < 0 || vy < 0 || vx >= 11 || vy >= 9) return

  // 玩家在视口中的位置（边缘相机夹取时不是 5,4）
  const px = game.player.x - game.camera.x
  const py = game.player.y - game.camera.y
  const dx = vx - px
  const dy = vy - py
  if (Math.abs(dx) + Math.abs(dy) !== 1) {
    // 不是相邻格：吸附到最近的相邻格
    if (Math.abs(dx) >= Math.abs(dy)) step(dx > 0 ? 1 : -1, 0)
    else step(0, dy > 0 ? 1 : -1)
    return
  }
  step(dx, dy)
}
```

**吸附规则**：玩家点得不准时，按"主轴优先"吸附到上下左右最近的一格。不要允许斜走。

### 7.6 唯一的缓解手段：让栈底那层"有用"

`followHand` 已证无效，右滑关不掉。所以只剩结构手段：**保证页面栈深度 ≥ 2，让右滑落在"上一层"而不是"退出应用"。**

但垫哪一层是有讲究的。垫一个空白的"已暂停"页，玩家会觉得莫名其妙多了一次跳转；**垫标题页则完全自洽**——它本来就要存在。

#### 推荐形态：标题页当栈底

```
启动 → Title（栈底）→ 玩家点「继续/开始」→ push Game    栈：[Title, Game]
游戏中右滑 → 系统 pop 掉 Game → 回到 Title             栈：[Title]
玩家再右滑 → 退出应用（可接受，这是标题页）
```

好处：

1. **不新增页面**。标题页本来就在 M1 的界面清单里（GDD 5.1），现在它多了一个职责；
2. **右滑语义合理**。从游戏退回标题，是玩家能理解的"退出到主菜单"，不是"应用闪退"；
3. **存档语义自然**。回到标题 = 一局结束，正好触发一次自动存档；
4. **第二次右滑退出**在这里是可接受的——玩家已经在主菜单，退出应用不损失进行中的进度。

#### 必须处理的三个问题

1. **Game 页会被销毁**。系统 pop 会走 `onDestroy`，页面 `private` 里的数据全丢。
   → 游戏状态必须放在页面外（`globalThis` 或 `storage`），回到 Game 时从状态重建视图。
2. **任何模式都可能被打断**。玩家可能在战斗中、对话中、商店里被弹回标题。
   → 每个模式都必须"可从状态重建"，不能依赖"页面实例还活着"。
3. **首启不能自动跳**。否则从标题弹回后又被推回游戏，形成循环。
   → 用 `entered` 标记，只在第一次自动进入。

#### 存档点：回到标题页的那一刻

这是标题页方案最实际的收益——**进程还活着**。

| 场景 | 进程 | 异步写入 |
|---|---|---|
| 栈底右滑退出 | 结束 | 来不及 |
| 游戏中右滑 → 回标题 | 存活 | `storage.set` 几毫秒就落地 |

所以存档写在 `Title.onShow`（用 `inGame` 标记只在"从游戏回来"时触发），而不是只写在 `Game.onDestroy`。标题页上要显示"已自动保存 · Lv12 · 15:03"，这行字就是"现在可以安全退出"的凭证。

即使玩家立刻再右滑退出，上一步的写入已经完成——不需要依赖"人不会连滑两次"。

#### 实测支撑

- 守卫页版实测：Game 右滑 → 回守卫页，**计数保持不变**；
- 「共享标记」`G Q G` 能接上，说明 `globalThis` 跨页面共享成立，状态可以活过页面销毁；
- 守卫页再右滑 → **退出应用**（所以垫层只有一层缓冲，别指望更多）。

#### 代价

- 启动多一次 `push`（约几十毫秒 + 一次切换感，可用纯色过渡掩盖）；
- 游戏页重建有一次重绘，重吗？取决于地图节点数，M4 用 99 格实测；
- 多一个页面常驻内存（标题页只有几个文本 + 一个按钮，可以忽略）。

#### 不推荐的做法

- **垫一个空白页**：语义不通，玩家不知道为什么被弹到一个空界面；
- **垫层 + 自动 push 回游戏**：会形成"弹回—推回"的拉扯，且没有增加任何安全性；
- **垫两层以上**：多买一次缓冲，代价是两次莫名的页面切换，不值。

#### 实现要点（已验证）

```js
// Title 页
onShow() {
  if (!store.entered) {
    store.entered = true
    setTimeout(() => router.push({ uri: '/game' }), 60)   // 首启直接进游戏
  }
  // 之后每次回到这里 = 玩家右滑回来了，停在标题页等操作
}
```

**三条硬约束**：

1. 状态不能放页面里（Game 被 pop 会 `onDestroy`）；
2. 本地 `.js` 模块**可以用**（ESM 默认/命名、CJS、无扩展名、两页共享都验证过）；曾遇到一次模块体被编译成 `() {}` 且无法复现，判为构建缓存问题——构建脚本要加哨兵串校验，见 `docs/构建与模块验证.md`；
3. 首启只自动跳一次。

## 9. 验收标准

- 点相邻格 20 次，20 次走对；
- 点不可走格，不移动、不卡死、有一行提示；
- 相机在 4 个边缘都正确夹取；
- 门/楼梯优先于遭遇；
- 遭遇只在走步后触发；
- 边缘起手的拖动不移动（记录为 blocked）；边缘点按仍能走一格；
- 中心竖向拖动可连走，松手即停；
- 横滑不移动（已定案，不再有"按结果决定"）；
- 99 格重建 < 50ms；
- 切图期间输入全部丢弃；
- 暂停按钮随时可点。
